# dsh-media-hub

A DeepSeek Harness (DSH) media hub (formerly Video Sync): search shows, novels, ebooks and papers across sources (command line extensions, `docs/extensions.md`), watch together (each viewer streams their own copy of a file served by DSH: a local file, a show from a source, or a video or playlist from any site yt-dlp reads; play, pause, seek, rate and episode changes are synced through a small room server inside DSH), and download books in a chosen format onto per-person shelves.

## Layout

- `index.js`: Host plugin (`media-hub` row). Provides the `mediaHub` service, mounts the `/media-hub` routes (media, subtitles, the page's modules, the JSON API), the Fetch routes under DSH's `/api/media-hub` (the shelf; looking up, fetching and opening a room: there `requestIdentity` names the person) and the room WebSocket.
- `tools.js`: the assistant's `videosync` tool (`media-hub-tools` row; the tool keeps its name so a rename removes no tool from running sessions). Looks the service up at call time, so a reload of the Host row never unregisters the tool.
- `client.js`: Web UI half in DSH's Client module format: it loads the page's files from `/media-hub/web/<build>/` (the build the Host names in its settings, so an update swapped into an open page brings the new files), keeps the panel's width on `.vsync-page` for the layout; the sidebar entry (the `label` setting, else the page's name in the viewer's language), registering the words from `locale/` before the entry and page show, the chat starter for "Ask" buttons and registration.
- `web/`: browser ES modules and styles the Host serves (any `web/*.js|css` by name): `page.js` (the three tabs and the URL state, or one room), `nav.js` (tab, source and category in the URL and in the browser's memory, pure), `continue.js` (which shows "continue watching" lists, pure), `watching-view.js`, `discover-view.js` (source picker with All sources, categories, search, book filters), `result-card.js` (a show or audiobook result as a card), `books-view.js` (book filters, a book result card, My books), `device-copy.js` (a book's copy on this device: a download link, or in the iOS home-screen app a kept copy shared through the share sheet or opened in Safari), `resumable.js` (fetching a whole file, carrying on after a dropped connection, pure), `details.js` (what is known about a work, shared by results, the library and the room), `about-view.js` (a room's About tab), `avatars.js`, `format.js` (counts and labels per language, pure), `rooms-view.js`, `library-view.js` (the library list), `library-card.js` (the one card a show or a book is drawn in), `room-view.js`, `ui.js` (shared helpers, icons, controls), `boundary.js` (what the panel shows when the page throws while drawing), `player.js`, `picture-click.js` (what a click or tap on the picture does, pure), `panel.css`. They import `src/sync.js`, `src/formats.js` and `src/i18n.js` by their served names (`./i18n.js`), which also run in Node; tests resolve those names through `test/fixtures/web-modules.mjs`.
- `src/work.js`: the snapshot of a work kept with a show (pure). `src/media.js`: the hub the routes and the tool talk to, wiring rooms, library, downloads, sources and the watch log. `src/hub.js`: rooms, sockets, preparing. `src/sync.js`: clock offset and drift math, pure. `src/room.js`: room state and operations, pure. `src/library.js`: scanning a path into episodes, subtitles, what a file needs. `src/shows.js`: the library manager (shows, sizes, delete, rename, keep, watch progress, auto-delete, resume, posters). `src/downloads.js`: per-show want lists run as ranges. `src/cache.js`: the rolling cache (what to have on disk, trimming, the cap) over `src/window.js` (its arithmetic, pure) and `src/episodes.js` (a show's episode list from its source, matching files by number). `src/covers.js`: every picture (covers, posters, room previews) behind one route and cache: made by the source (its `cover`) or as an ffmpeg frame of a file (the browser never sees a source's picture URLs). `src/hosts.js`: per-host rules (patterns, hosts files), shared by `src/proxy.js` (the `proxies` setting, which route a request to a host takes, and fetching through it) and `src/cookies.js` (the `cookies` setting: which person's signed-in account a site is read with, and a private copy of its cookies per run). `src/sources/`: sources: `command.js` runs a configured command speaking the protocol in `docs/source-protocol.md` (episodes, or one book file in a format); `link.js` is Link, any address yt-dlp reads, with a quality choice, subtitles and progress; `ytdlp.js` what the hub asks of yt-dlp and reads back (progress lines, failure reasons, subtitle languages, pure); `process.js` runs their programs; `index.js` builds them from the config. `src/filters.js`: search filters applied to every answer and the merge of several sources' answers (pure). `src/books.js`: shelves (per person entries, shared files, conversion with `ebook-convert`, the disk cap). `src/formats.js`: what a book is offered in (pure). `src/i18n.js`: picking a text per language and the book language filter's choices (pure, also served to the page). `src/locales.js`: reading `locale/<tag>.json` for `/media-hub/api/locales` (with `@soffits/dsh-host-kit`). `locale/`: one file per language (`meta` for DSH's plugin manager, `ui` for the page's words); no language is named in code. `src/people.js`: the person behind a request from `requestIdentity`, or the single owner. `src/points.js`: extras a person's points pay for (a new series, a binge night), asked of the points plugin's `points` service (@soffits/dsh-points), which also shows the offer in the page. `src/shelf-routes.js`: the shelf's Fetch routes. `src/person-routes.js`: looking up, fetching and opening a room as the signed-in person (Fetch routes under DSH's `/api`), and the helpers both share. `src/watchlog.js`, `src/journal.js`: the watch log. `src/prepare.js`: ffmpeg remux/transcode; `src/preparing.js`: which episodes are prepared when, from where the rooms are (pure). `src/http.js`: routes and Range serving. `src/delivery.js`: where media URLs point. `src/json-file.js`: reading and saving the state files (an unreadable one is moved aside, never overwritten). `src/events-route.js`: the page's change stream (`GET /api/media-hub/events`). Code shared with the other plugins of this kind (the locale reader, change notices, event streams) comes from `@soffits/dsh-host-kit`, bundled into `dist/`: fix it there, never copy it here. Shared helpers: `src/errors.js` (`codedError`, an Error with the code the routes map to a status), `src/limit.js` (`createLimiter`, at most n jobs at once), `src/sha256.js` (a file's hash, streamed).

## Checks

`dist/` is the built plugin (`npm run build`: index.js and tools.js with `ws` and schemastery bundled, plus hls.js's browser build); DSH imports it, so it is committed and CI fails when it is stale. After changing `index.js`, `tools.js` or anything under `src/`, run `npm run build` and commit `dist/`. `web/`, `client.js` and the `src/` modules the page imports are served as they are and need no build. The reason: at DSH's boot a link-installed plugin could not resolve its own packages (`ws`, schemastery); with none to resolve, it loads every time.

`npm run check` (syntax of every file), `npm test` (Node test runner, offline). `npm run test:browsers` boots a throwaway DSH home with the plugin linked and drives two Chromium contexts through a room and a book download, and an iPhone-sized WebKit (the engine of every iPhone browser) through saving a book in the home-screen app; it needs a `dsh` binary, a Chromium, and Playwright's WebKit (`npx playwright-core install webkit`, its system libraries with `install-deps webkit`), and never touches a real DSH home. Anything a phone shows is checked there in WebKit, at the panel widths a phone gives, before it ships.

## Design rules

- The room state on the server is the truth: `{ items, index, playing, position, rate, updatedAt }` with server timestamps. Clients compute the expected position from it with their measured clock offset, never from each other.
- Opening a room, episode changes, seeks and stalls go through the ready gate (`src/room.js`): the clock holds until every connected viewer reports ready, then starts at a server time slightly ahead.
- Drift: under 0.3 s ignore, 0.3 to 2 s nudge the playback rate by about 5 %, over 2 s seek.
- The sync channel is the plugin's own WebSocket, separate from the Web UI's connection, so a Web UI reconnect does not touch playback. A dropped socket never stops local playback; the next state snapshot resyncs.
- Only browsers DSH admits (`connection.admit`, owner principal) reach any route. Display names are attribution, not authorization.
- Nothing from a site reaches the browser directly: media and pictures are served by DSH, and what the hub fetches itself takes the route the `proxies` setting gives its host, failing closed.
- Media delivery is behind `src/delivery.js`; the default serves from the DSH origin. Other deliveries (object storage with signed links) plug in there.

## Working on the project

- Everything in the repo (code, docs, commits) is English, except translations and files deliberately in another language.
- Ordinary implementation choices are yours: decide, write the choice and its one-line reason under the right system group of `docs/decisions.md` (replacing any line it supersedes, no dates), and mention it in your report. Product decisions (what players get, direction, scope, taste) belong to the maintainers and live in `docs/roadmap.md` only; ask about those.
- If a requested approach looks weaker than an alternative, say so with the reason before building it.
- Report each state separately: implemented, tested (which checks, which real run), committed, pushed, CI. Say plainly what was not verified.
- Commit on a branch as you go. Merge to `main`, tag, release or publish only when the task asks for it.
- Work only in this checkout, on the current branch. Make no folders or worktrees outside it; builds people test come from the build's own output folder, given by path. Temporary files go under the build folder or a git-ignored path and are removed when done.

## Delegating to subagents

Do the work yourself, in your own session, by default: design, code, fixes and review. A subagent starts cold, re-reads what you already know and hands back a summary you must check, so it usually costs more than it saves. Hand off only work that is simple and would burn your context for little (a mechanical sweep over many files, a long log to search, a bulk rename), to a smaller, cheaper model that fits the job.

- A brief says what and why, not how: the goal, the decisions that apply, the non-obvious constraints, which files it owns, the checks that decide "done", and a progress file to write early and update after each step. Leave out methods nobody chose, so a capable model can find a better way.
- When you do hand off, parallel subagents only on disjoint files. Each shared helper has one owner; tell the others to use it or wait for it.
- A subagent's summary is a claim. Read its diff and rerun the checks before building on it.
- If a review is asked for, the reviewer is at least as strong as the writer (a weaker reviewer makes strong code worse) and marks each finding *likely* (hits ordinary use: data loss, crash, wrong result) or *rare* (hostile input, odd timing, limits nobody reaches). Fix the likely ones with a regression test; put rare ones in `docs/queue.md` unless the fix is cheap and local.

## Long work

- Any run can be cut off (limits, restarts, context compaction). For work longer than a few steps, keep `docs/progress/<task>.md`: the goal, what is done, decisions, what is next. Update it after each meaningful step so a fresh session resumes without redoing work. End it with `## Final` (what was done, checked, left over). It is a working note: when the work merges, move what lasts into the decisions and queue docs and delete the file.
- Finish the whole goal in one run. Don't end your turn to "wait" for something while work remains you can do.
- Leftovers and known bugs go into `docs/queue.md` the moment you find them, not into a promise in your report.

## Before building

- Before writing any non-trivial component, search the community and current research for maintained libraries and better approaches. Check the licence (MIT/Apache/BSD/CC0 to ship; GPL, non-commercial and unlicensed work only as ideas, reimplemented), upkeep, and that it runs on our versions. Adopt, adapt or write our own, and record why in `docs/decisions.md`.
- Take versions of languages, tools, frameworks and dependencies from current official sources, not memory; they change faster than training data.

## Code

- No backward compatibility while the project has no users: when a format or name changes, change it everywhere and delete the old one.
- Few general mechanisms, no special cases. When something breaks, fix the shared layer or the data, not the one call site. No hard-coded lists of names, no matching on error text, hostnames or model names as a substitute for a real signal.
- Define each list, limit or constant once and derive variants from it.
- Reproduce a bug before fixing it; a confident guess from reading code is often wrong. If two fixes built on one assumption fail, the assumption is the bug.
- CI is where tests run. Locally, compile and run only a quick check you need while writing; push the branch and let CI run the suites.
- Keep CI time low. CI runs on pull requests and `main`, not on every branch push. One release is one branch and one pull request (no stacked PRs per feature). Commit locally as often as you like; push and open the PR when the first sizeable part compiles, keep working on the same branch, and push the next batch when ready (a newer push cancels the older run). Don't sit watching a run (no sleep-and-poll loops): keep working and check its result between steps; when nothing but the CI result is left, say so in your report and end the turn. Never wait on a test run: if a local run is truly needed (a failure CI can't explain), run it in the background, keep writing code, and fix what it reports when it ends. Write each check once, at the cheapest level that can see it (unit test when no running game or server is needed, an integration or game test only for what needs one, a client or screenshot test only for what needs the screen), and extend an existing test before adding one that repeats its setup. Docs-only changes start no run (`paths-ignore` on both triggers), but GitHub judges a pull request by its whole diff, so push docs and progress notes together with the next code batch, never alone to a PR that has code.
- If a test can't pass, explain why in the progress file. Never loosen or move an assertion to make it green.
- Split a file by responsibility before it grows past about 500 lines (generated code and static data excepted).
- No dead code, commented-out code or bare `TODO`; unfinished work is in `docs/queue.md`.
- README and other public docs are for users. Notes for maintainers and agents go here or in `docs/`.

## Git

- Conventional Commits, one-line subjects, a body only when the why isn't obvious. The repo's local author identity is set on purpose; never override it.
- Squash merges by default. Whoever merges a branch deletes it, local and remote, in the same step (`gh pr merge --squash --delete-branch`), removes its worktree and runs `git fetch --prune`; only `main` and the current release branch stay.
- PR titles are Conventional Commit subjects (`feat: ...`, `fix(scope): ...`), because a squash merge makes the title the commit on the default branch; CI checks it.
- In GitHub Actions, reference well-known actions by major tag (`@v5`), not by commit SHA.
- Releases: move the `Unreleased` part of `CHANGELOG.md` under the new version's heading (English), bump the version, squash-merge to `main` with a Conventional Commit subject (`feat: <summary> (vX.Y.Z)`), and once CI is green on that commit push the tag `vX.Y.Z`; `.github/workflows/publish.yml` publishes to npm by trusted publishing (OIDC, with provenance, no stored token; the package's trusted publisher on npmjs.com names this repo and `publish.yml`, so renaming either breaks it) and creates the GitHub release with that section as the description, without rerunning tests. Don't publish by hand. Don't name a working branch exactly like the tag: `git push origin vX.Y.Z` then fails as ambiguous (use `refs/tags/vX.Y.Z`).
- Versions follow semver, and the bump comes from the commit types since the last tag, not from feel: below 1.0, `feat` or a breaking change (`!` / `BREAKING CHANGE`) is a minor bump and `fix`/`perf` a patch; from 1.0, breaking is major, `feat` minor, `fix` patch; docs/ci/chore/test alone need no release. The release check (`.github/workflows/release-check.yml`, `.github/scripts/release-bump-check.py`) fails a tag whose bump is too small; run the script with the new version before tagging.
