# Decisions

## Sync

- **Server state is the truth, with server timestamps.** Each viewer measures its clock offset (NTP-style, the ping with the shortest round trip wins) and computes the room position itself, so a 250 ms round trip between continents costs nothing. Same model as SyncTube and Syncplay; neither is reusable as a library (Haxe app, desktop client).
- **Drift: under 0.3 s ignore, 0.3 to 2 s change the rate by 5 %, over 2 s seek.** Rate changes are inaudible at 5 % and avoid the rebuffer a seek costs. A player already catching up keeps going until it is within 0.1 s, so it does not stop at 0.29 s and drift back.
- **A ready gate, as in Jellyfin SyncPlay's waiting state and Plex's waiting room** (`src/room.js`). Opening a room, a seek, an episode change and a stall stop the clock; each viewer present reports `ready` for that gate (by id, so a late report for an older gate does not count) once its player says it can play (`web/readiness.js`); then a playing room starts at `now + lead`, the lead being the slowest viewer's round trip plus 250 ms, within 0.3 to 2 s (Jellyfin: twice the highest ping, at least 0.5 s). Before, the clock ran from the moment someone switched episode, so whoever loaded first played while the other was still loading; a start at a future server time also keeps the state's trip across the network out of the start. Every seek goes through the gate: a seek into what is already buffered costs about the lead, below the 600 ms after which the waiting room shows, and it saves telling apart buffered from unbuffered positions per viewer.
- **Ready means the element can play (HAVE_FUTURE_DATA, the state behind `canplay`) with 3 s buffered while the browser still fetches, or whatever it fetched once it stopped** (no `progress` for 1 s). Safari on iOS loads little or nothing for a paused element, so a buffered-range test alone held an iPhone at the gate for good; Jellyfin SyncPlay also goes by the element's own events, not buffered ranges. A player held 1.5 s without being able to play is primed once: played muted until playback starts (muted needs no tap), then paused and put back. Still loading after 8 s, the viewer gets a "tap to keep loading" button that primes from the tap.
- **WebKit keeps one `<video>` and swaps its source**: it lets an element play with sound only once that element was played from a tap, so an element swapped in could not start. Detected by `webkitSupportsPresentationMode` (WebKit only), not the user agent. The viewer's first tap in a room plays and pauses the element muted for the same reason.
- **The next episode loads in a second `<video>` and is swapped in at the switch** (`web/player.js`): from the start for an episode under two minutes, else in its last 30 s, so an automatic advance finds it buffered, passes the ready gate in the same pass and starts at the usual lead, with no waiting room. The host already prepares episodes in order well ahead, so nothing changes there. Not on WebKit (above), for hls.js playback, nor while the finished video is full screen or in picture-in-picture (swapping would drop it), where the old load path runs; volume and mute carry over. Viewers do not report "next ready" ahead of the switch: the gate already needs every viewer's ready, which a preloaded element gives at once.
- **"Start without" appears after 10 s and is a choice, not a timeout.** A wait that silently gave up (the old 15 s hold) let one viewer fall behind unnoticed; now the others see who they wait for and decide. Those left out catch up on their own, and their stalls are ignored for 30 s, so a bad line cannot freeze the room in a loop.
- **A stall is buffering for over 1 s while the room plays, reported once per stall.** The room goes back to the stalled viewer's position (at most 10 s back; the others have that buffered behind them) and the others count as ready, so only the stalled one is waited for. Stalls in the 3 s after a start are the players spinning up and are ignored.
- **Who is waited for is whoever is connected now**: a viewer who joins while a gate is open is waited for, one who leaves is not; joining a room that plays does not stop it. A room everyone left, and every room after a restart, closes its gate again so the clock does not run on while nobody watches.
- **An episode still preparing or downloading is nobody's ready**: the gate closes only on an item whose file is ready, so the rolling cache's "preparing" holds the room like a slow viewer.
- **No host role.** Anyone in the room may play, pause, seek or switch episodes; the server orders operations as they arrive. Episode ends are reported by every viewer with the index they ended, and only the first moves the room on.
- **Operations from the player's own controls are told apart from corrections by expectation windows.** Each command the sync engine gives the player sets what it expects to see next (a play, a seek to a position) for 1.5 s; events matching an expectation are not reported.

- **Rooms close by themselves when nobody is in them**: 30 minutes after the last viewer leaves; a room nobody has opened yet lasts a day, so a link sent ahead of time still works.

## Packaging

- **The plugin is imported from a committed, bundled `dist/`** (esbuild, `scripts/build.mjs`): `ws`, schemastery and the proxy agents are bundled into the two entries and hls.js's browser build sits next to them, so loading needs no bare package resolution. A link-installed copy twice failed at DSH's boot with "Cannot find package 'ws'" though the clone's `node_modules` had it; dsh-oh-my-claude avoids the class of problem by having no runtime packages. The browser modules (`web/`, and the shared modules under `src/` listed in `MODULES` in `src/http.js`) are served as they are. CI rebuilds and fails on a stale `dist/`.

## Transport and access

- **The sync channel is the plugin's own WebSocket** on DSH's web server (`registerUpgrade`), not the Web UI's `remote.mux`, so a Web UI reconnect or a profile reload of other plugins does not touch playback.
- **Every route goes through `connection.admit` and requires the owner principal**, like DSH's own API. Every browser DSH's login admits is the owner, so everyone signed in may use rooms; display names come from the sign-in plugin's profile endpoint and are attribution only.
- **The panel can only start rooms from the library folders; the assistant's tool can open any path.** Browsers are owners anyway, but a browser listing arbitrary server paths is needless exposure.
- **Media is served by DSH's own web server by default** (`src/delivery.js`). Object storage with signed links is a named option behind the same interface, not built yet.

## Players and media

- **A link is downloaded, not embedded: YouTube is one yt-dlp site among the others** (`src/sources/link.js`). Before, YouTube played in its own embedded player in each browser. Downloading through the same rolling cache as any source gives every viewer the same file from DSH, so a viewer whose network can't reach the site still watches; sync gets the whole path (rate nudging, the ready gate on real buffers, the preloaded next episode) instead of seek-only correction past 1 s; ads no longer split a room; and the library and room cards get frames like any file. The cost was measured: a 10-minute 1080p60 video downloads in about 9 s here, and yt-dlp's merged MP4 (H.264/AAC, index first) is served as it is with no transcode; a long video starts after its first file lands, and disk stays under the cache cap. The embed's code (its postMessage player, title lookups, seek-only drift) is gone, so one player and one sync path remain.
- **Local media is made browser-friendly once and cached**: fast-start MP4 by remuxing when the codecs fit, H.264/AAC when they don't, cached by path, size and modification time. ffmpeg runs one job at a time at low priority.
- **hls.js (Apache-2.0) only where the browser lacks native HLS.** Loaded on demand from the Host, never bundled into the page.
- **Subtitles become WebVTT.** SRT in JS; ASS/SSA and text tracks inside MKV through ffmpeg. Text encoding is detected (UTF-8, UTF-16 by BOM, then GB18030, Big5, Shift_JIS, EUC-KR), so Chinese, Japanese and Korean releases display correctly.

## Library and sources

- **A show is a folder of episodes (or one file) directly inside a library folder; its id is its path.** Notes the files can't hold (source, total episodes, per-episode progress, finished episodes, where each viewer stopped, keep, watched time) live in `shows.json`, keyed by path and moved on rename.
- **Watch progress is per show, shared by everyone who watched together**: people watching together expect one state. Each viewer's own last stop is kept too and shown only where it differs.
- **A show is watched when its last episode was watched, or every episode; an episode is watched from 90 % on (the last 10 %, at least 3 s, at most 5 min).** Credits and closing a few seconds early still count; a show still downloading isn't watched until its last episode is there.
- **Auto-delete runs hourly and skips kept shows, shows an open room plays and shows downloading.** Deleting can't be undone, so every rule that could be wrong errs on keeping.
- **Sources are small objects with search, info and download** (`src/sources/index.js`); the library and rooms only see the files a source writes.
- **A source is a configured command speaking a JSON protocol** (`src/sources/command.js`, `docs/source-protocol.md`): no site is known to the code, so a new site is a command and a config entry, never a plugin change. The command decides its own network route (a launcher requiring a proxy, for example). Fanqie and bookfetch are the default config entries; fanqie-cli grew `--json` for it rather than the plugin parsing its text. The protocol's verbs and flags are fixed (the config has no per-verb argument templates), so every wrapper looks the same.
- **Link is the one built-in source, over yt-dlp** (`src/sources/link.js`): the hub calls yt-dlp itself instead of through a wrapper command, because yt-dlp is already a generic tool for over a thousand sites, Link takes addresses rather than searches, and the per-host `proxies` setting needs to pick the route per page. `info` is `yt-dlp -J --flat-playlist --no-playlist` (a playlist's entries are the episodes, a video inside a playlist plays alone, as pasted); `download` is one yt-dlp run per range (`--playlist-items A:B`, files named by number, partial files under `.incoming`, `--print` JSON at `before_dl` and `after_move` for progress), so the library, rolling cache, follows and rooms need nothing new. Quality maps to format sorting, `-S res:<height>,vcodec:h264,acodec:aac` (the best up to the height, preferring what browsers play without a transcode; `auto` is `maxHeight`), or `-x --audio-format m4a` for audio only; a show keeps its quality and passes it to every download.
- **Files a source reports done are checked** against the size and sha256 it reports, one by one as they land; a mismatch deletes the file (the command would skip it as present) and counts as failed. A run that exits 0 without a `result` line is an error: a wrapper that dies quietly must not look like a finished download.
- **A show from a source is a rolling cache, not a copy** (`src/window.js`, `src/cache.js`): its directory lists every episode (the source's count; titles show once a file exists, though the protocol's `info` carries them), a window of the current episode, the next `cacheAhead` and `cacheBehind` just watched is on disk, the rest is fetched when someone goes there. Disk was the constraint: a 450-episode drama is gigabytes, and the first version fetched all of it for any "watch".
- **Downloads are per-show want lists run as ranges, one at a time.** The cache says which episodes to have, in order; the runner turns the first missing one and the missing ones right after it into one `--episodes A-B` run (the command skips finished files; the sha256 of each new file is checked here). A new first episode that the running range will not reach cuts the run and restarts it there, so a jump is fetched at once; a show with a room open goes before one without and interrupts it. A failed job stays failed until someone asks for an episode again or taps retry, so a broken source is not hammered by every progress tick.
- **What is trimmed: watched, outside every open room's window.** Skipped (never watched) episodes stay for the cap to deal with, and an episode deleted by hand is not fetched again until someone goes to it: deleting errs on keeping, like the rest of the library. The watch log and the shared progress keep episodes by file name, matched to episodes by the number the name starts with, so a dropped file still counts as watched.
- **A show kept offline is a flag, not a copy mode.** Pinned shows are fetched whole from the focus on and never trimmed or evicted; unpinning returns them to the window. They do not count against the cap: the owner asked for them.
- **The cap evicts least recently watched first, never inside an open room's window.** Last watched is the latest of the show's progress time and the file's time. The cap is checked when a download lands, after a plan, hourly and at start; a window larger than the cap simply stays.
- **Rooms list every episode from the start.** Items carry their episode number (`slot`); one not on disk is `remote`, or `preparing` once someone stands on it, and joins the usual preparing flow when its file lands. The room therefore opens at once on "watch now", where the first version waited for episode 1.
- **A source's command runs in `<stateDir>/<source id>`.** A tool's own defaults may put state files in the working folder (fanqie-cli did, before its launcher passed the paths); a plugin must not depend on that for where files land.
- **Fanqie dramas (HEVC, 1080×1920 portrait) are transcoded to H.264 at 1080 lines (608×1080)**: about 10 s per 80 s episode on two threads, half the size of a full-resolution transcode, and a portrait picture shows at most screen height on a landscape screen anyway. Episodes prepare in order from the one the room opens on, well ahead of playback.
- **A frame is the picture of anything without a cover**: a show's poster is a still of its first episode 3 s in, a room's preview a still a tenth into the episode playing, both made with ffmpeg the first time a browser asks for them and cached by file, size and modification time.

## Network

- **One per-host proxy setting for everything the hub fetches itself** (`src/proxy.js`, `proxies`): rules of a proxy URL and host patterns, first match wins, others direct; every yt-dlp call gets `--proxy` (an empty one when nothing matches, so the hub's choice stands), and the hub's own picture fetches use an agent for the route. No country or site is named in code: the owner lists them. Patterns read like a domain list (`name` covers the name and every subdomain, `.suffix` a whole ending, `*` everything) and a rule can take them from a file that is re-read when it changes, so one list can serve this setting and other tools (a browser's PAC file). A request may name the page it belongs to and takes the first rule naming either host, so a thumbnail on a CDN nobody listed goes the way its site goes. It fails closed: a hosts file that can't be read, or a proxy that is down, fails the request instead of sending it direct.
- **socks-proxy-agent and https-proxy-agent** (MIT, the proxy-agents monorepo npm itself uses) for the hub's own requests: small, stable, every scheme yt-dlp takes (`socks4`, `socks4a`, `socks5`, `socks5h` with names resolved by the proxy, `http`, `https`). undici's `Socks5ProxyAgent` is still experimental (it warns on construction) and would bundle all of undici.

## Watch log

- **Append-only JSON Lines, written by the room server from the operations it already applies.** No client reports, so a viewer can't skew it; `position` lines at leave, episode change, close and every two minutes while playing give "where we stopped" per viewer without logging every pause.

## Web UI

- *Ask* goes through `ctx.uiActions.chat` from @soffits/dsh-ui-actions: one shared item card and model format for every plugin page, instead of each page writing its own Markdown draft. The hub keeps its own button for its card layout.
- **The page is browser modules served from `web/`** (`page.js` and what it imports), with React handed over by `client.js`, so the page can grow past one file and still needs no build step. `client.js` keeps the words and the registration.
- **Three tabs: Watching, Library, Discover.** What people do with the page is three different things (see who is on and pick up where they stopped, manage what is on disk, find something new), and putting them in one column buried the rooms and the library under the search. Watching is the default because it is what a returning viewer wants; Discover keeps its search and results while another tab is open.
- **Discover is source first, then category, then search.** The picker lists every configured source in config order, then *Link* (the reserved id `link`, listed by the host when yt-dlp is installed, with `input: 'url'` so the page takes an address instead of a query and has no categories; All sources leaves it out). Labels and categories come from the `sources` config; the page only translates the category ids it has words for, and shows the configured label otherwise, so no site is known to the page. A web address typed into a source's search box moves to Link instead of being searched; Link looks it up and shows the one work as a result card, with the same actions as any result and a quality picker.
- **The place is in the URL query with a `vs-` prefix** (`vs-tab`, `vs-source`, `vs-kind`), written with `pushState` for a tab change (back walks the tabs) and `replaceState` for source and category, and removed when the page unmounts. The default tab and Discover-only values are left out when they do not apply. DSH's own panel selection is not in the URL, so `client.js` selects the panel when a `vs-*` parameter is present, as it does for a room link. The last source, and a category per source, are also kept in `localStorage` (the URL wins over memory, memory over the first entry).
- **Related works are rows that open the work, not cards with Details of their own.** A card inside Details with its own Details nested forever. The row opens the work as the focused view of Discover (its id in `vs-work`, pushed on the history so back returns to the list or the work before, and a refresh keeps it); the work's own Details then list its related works one level down, and so on, one view at a time (`web/details.js` is the one component for what is known about a work).
- **"Continue watching" is a library show with a resume point or a finished episode, not watched to the end and not in a room**, ordered by `lastWatchedAt` (the resume point's time) with the library's order for shows without one.
- **The library keeps a snapshot of its work** (`work` in `shows.json`, `src/work.js`): what `info` returned when the show was saved or watched (no extra request), related works one level deep, episode titles. Library rows, the room's About tab and episode titles read it, so looking at a show never asks the source. Shows saved before are backfilled once, one at a time with a pause, quietly; a failure is noted and not retried automatically (Refresh info by hand does); nothing else repeats it.
- **A related work from a room opens in a new tab**, not in the room's tab, so someone in a room is never taken away from it by a click.
- **The next season is a related season whose title extends this one's.** Sources give seasons as related works without an order; a title stem ("X", "X第二季") is the only signal, and a wrong guess only shows a button.
- **Avatars are the signed-in person's picture when the sign-in plugin gives one, else initials on a colour from the name.** The sync channel carries names only, so other people show initials until identity is carried there (queue).
- **Following looks for the next season by watching the related list** (`src/follow.js`): the source's `info` has no release dates or reservation flags that we have seen (Fanqie's search and info carry none), so a followed show is asked about once a day, jittered, one at a time with a pause (never more than once an hour for the same show, which is also how often opening it may trigger one), and a related *season* that was not there when following began is the new season. It is added as an empty show (nothing downloaded until someone watches), grouped with the earlier seasons by a `group` key, and followed itself; a failed check waits until the next day instead of retrying. Episode counts growing in the same call extend the season in progress. News (`newSeason`, `newEpisodes`) stays on the show until someone dismisses it. If a source ever reports an upcoming season with a date, the check could be moved to that date.
- **Sorting is done on the page, on the results already loaded; paging is the source's to offer.** Sources answer in their own relevance order (the default); "most played" and "newest" reorder what is loaded by the `popularity` count and the `updated` fact, and an order is offered only when at least two results can be told apart by it. A source with more pages says where the next starts (`next`), the host passes it back as `--offset`, and the page appends the new works, dropping repeats and ending the list when a page adds nothing, so a source that ignores `--offset` cannot loop. Fanqie's search takes an `offset` in its request, but a check against the live app (once) returned the first page's works again for another offset, so fanqie-cli does not offer `next` and Fanqie has no Load more.
- **Destructive actions confirm in place** (the row turns into the question with Cancel and Delete), not with the browser's `confirm` dialog, which looks foreign in DSH.
- **A global panel (sidebar entry + main column)**, like DSH's own Automation tasks page. A room link is the Web UI URL with `?media-room=<room>` (links made as `?videosync=<room>` before the rename still open it); the page opens on that room. DSH's sign-in may not return to the original URL, so the panel also lists open rooms.
- **Every picture goes through one pipeline** (`src/covers.js`): a work's cover, a show's poster and a room's preview are all `covers/<key>` routes served to admitted owners, made the first time someone asks and cached under one cap. A source's picture is fetched by that source (a command source's `cover` verb, so its launcher's proxy holds; Link through the `proxies` setting); a local file's is an ffmpeg frame. The browser never sees a source's picture URL, and a key hashes what made it, so the page can't ask the host to fetch an arbitrary URL. The page tries a work's pictures in order (a show: its cover, then its frame) and shows a placeholder only when none loads.
- **Descriptive result fields are raw and optional; the panel formats them.** A source sends counts and codes (`popularity {count,label}`, `status`, `episode_count`), the page formats "36.7万"/"36.7K" per language, so one source feeds both. Unknown labels and `meta` rows show their own words.
- **`related` is the source's list, not the host's guess.** Fanqie links sequels and other adaptations itself and seasons by title only; finding them is the source's job, the host shows what `info` returns, grouped by `relation`.
- **Words live in `locale/<tag>.json`, and no language is named in code.** One file per language, DSH's own convention (`meta` for the plugin manager, `ui` for the page); the Host lists the folder (`src/locales.js`, `/media-hub/api/locales`) and the page registers what it gets with DSH's locale store, which walks each language's declared fallback chain. A language is a file, not a code change; a test checks every file has every key of `en` with the same placeholders, and that no tag or CJK text appears in code.
- **The page's `t` carries the viewer's tag (`t.language`)**, and everything language-dependent that is not a sentence goes through `Intl` with it: counts (compact notation writes 万/亿 itself), sizes (unit format, so French reads "565 ko"), dates and times, language names, plural forms (`Intl.PluralRules` picking `<key>.one`/`<key>.other`). A per-language branch in code was the thing to avoid.
- **A text given per language is a `{ <tag>: text }` map, picked by exact tag, then primary subtag, then `en`, else its first text** (`src/i18n.js` `pick`, shared by Host and page). It serves the sidebar `label` and source and kind labels.
- **A configured label wins; without one the page's words for the id; else the id.** So the default sources carry no labels (their names are `source.name.<id>` in the locale files) and anyone can rename one in config without the locale files overriding it.
- **The book language filter offers languages from the data**: the viewer's own, the one picked, and those the results are in (`languageChoices`), instead of a fixed list in code.
- **Phones (≤ 640 px) get a compact card**: a fixed 64 px cover, the title and one ellipsized info line beside it, *Ask* as an icon in the card's corner. A book's single action (download in a format) sits beside the cover; a show's several actions take the full width under it, with *Details* beside the cover. Wider, the cover fills the card's height (`object-fit: cover`, top-aligned). Book filters fold behind a button with the active count. Touch screens get 40 px controls and 44 px tabs.
- **Tests load web modules the way the browser does**: a Node resolve hook (`test/fixtures/web-modules.mjs`) maps the names the Host serves from `src/` (`MODULES` in `src/http.js`) so the list exists once.

## Media hub and books

- **Video Sync grew into the media hub instead of a second plugin**: one Discover, one Library and one source protocol for every kind of work; a mode per kind (`media`) decides between rooms and downloads.
- **Book files come through the source command, never from the hub**: the same rule as covers, so a launcher's proxy holds for every request. Adopted ideas, not code: Shelfmark's filter set and per-result formats (it is a separate server with one global proxy), LazyLibrarian's convert-after-download with `ebook-convert` (GPL).
- **Shelves live under DSH's `/api` as Fetch routes**: only there does a `requestIdentity` provider know who asks; files stay on the plugin's own routes nowhere else. Shows stay shared (they are watched together in rooms).
- **A file per (source, work, format), shared by shelves**: two people downloading the same book keep one copy; the cap evicts files, never shelf entries.
- **Saving to the device is a link the person taps**, not an automatic download after the fetch: phones only treat a download they started as theirs (iOS hands an epub to Apple Books).
- **The state folder is not moved on the rename**: shows and the watch log name files by absolute path, so an existing `videosync` folder is used where it is.
- **The assistant's tool keeps the name `videosync`**: renaming it would remove a tool from running sessions.
